# 故障与修复记录 — 2026-10-22

## Asset 重构导致 Launcher 材质外观变化

### 现象

Asset 所有权重构后，Launcher 中原本具有明显环境反射与高光的球体变成较粗糙的非金属外观。此前仅验证了程序运行和退出，未充分验证画面与原有版本一致。

### 根因

旧 `MaterialAsset::Load` 只读取 `parameters`，而 DefaultWhite 文件使用 `scalarParameters/vectorParameters`，因此旧版本实际未设置 Metallic/Roughness。渲染参数构建使用默认金属度 0.8、粗糙度 0.2。

重构同时接通分组 JSON 解析后，文件中的金属度 0.0、粗糙度 0.5 开始生效。结构调整因此带来了未获要求的场景外观变化；此前将这项解析修正直接纳入重构，没有迁移默认资产的实际视觉参数。

另一个验证问题：上次最终留存的 `asset-launcher-before/after/running.png` 都是初始化白屏，不能作为视觉一致性的证据；固定等待时间和正常退出码不足以证明已经完成场景绘制。

### 修复

- 保留正确的分组材质参数解析，将 DefaultWhite 的显式材质数据迁移为原先实际生效的值：metallic 0.8、roughness 0.2。不在加载器或 Renderer 中硬编码场景兼容分支。
- AssetOwnershipTest 使用独立生成的测试材质，继续验证粗糙度 0.5 的分组解析、组件参数隔离及生命周期，避免与场景默认资产的美术参数绑定。
- Launcher 验证改为等待非白屏场景连续出现，再使用窗口内容抓取，避免其他桌面窗口遮挡截图。

### 验证与证据

- Langcher、Tests 的 MSVC Debug 构建通过；`Tests.exe -test=AssetOwnershipTest` 返回 0、stderr 为空。
- 分别运行保留的重构前 `out/build/x64-Debug/Langcher.exe` 与修复后的 `out/build/vscode-x64-Debug/Langcher.exe`，约 23.7 秒和 19.8 秒取得已绘制窗口；均通过 WM_CLOSE 正常退出 0。
- 人工检查两张截图，均显示原有金属球、环境反射及高光。窗口截图中场景区域 `(8,31)-(530,592)` 的 RGB 平均绝对差和最大通道差均为 0；此结果限定于本次启动场景、相机及窗口捕获，不代表所有场景回归已覆盖。
- 两次日志中的既有 Validation Error 数量一致：pCode-08737 四条、framebuffer-00892 一条、imageView-01026 一条、image-01000 一条；本次未修复这些既有错误。
- 原图与运行日志：`out/diagnostics/asset-visual-original-window/`、`asset-visual-fixed-window/`。
- 像素比较结果：`out/diagnostics/asset-visual-comparison.json`；构建及测试：`asset-visual-fix-build.log`、`asset-visual-fix-test/`。

## Engine 模块命名与注释编码统一（第一批）

### 范围与调整

- 按模块推进，本批处理 Engine；其他模块只更新对 Engine 成员的必要引用。Tests、Shader 和资产数据未改动。
- 18 个旧编码文件按 GB18030 正确解码后转换为 UTF-8；另修复 5 个 UTF-8 文件中已损坏的注释。Engine 的 70 个 C++ 源码/头文件现均可严格按 UTF-8 解码，且不再包含替换字符 U+FFFD。
- 数据成员按声明的访问权限统一：私有使用 m_ 加 PascalCase，保护使用 _ 加 camelCase（如 _localLocation、_worldTransform），公有使用 PascalCase；布尔成员在访问权限前缀之后保留 b 标识，如 m_bLoaded、_bVisible、公有 bValid。参数和局部变量使用 camelCase。Camera 保留私有成员的 m_ 前缀；ViewRect 的 X/Y/Width/Height、SceneView 的 SplitDepths、bDepthRangeZeroToOne 等公有字段保持统一命名。
- 按访问权限重新检查了 157 个私有/保护成员及其引用，覆盖 AssetRegistry/AssetManager、各类 Asset、Camera、场景组件/代理、材质、视口与实例数据模板。公有字段及嵌套结构体中的公有字段不添加外层类的访问前缀；不改变访问权限和资源管理行为。规则同步到 Doc/ai_contract/code_rule.md。
- 同步更新 Application 和 Renderer 中的视口、裁剪深度及级联阴影引用。没有改动调用方的其他命名或乱码注释，这些留待其所属模块迁移。
- Engine 的 MSVC 编译选项显式使用 /utf-8，并传递给读取其公共头文件的调用方。尚未迁移模块仍会报告编码警告，不将本批记为全工程编码清理完成。
- 检查到 Engine 的材质键哈希已使用 Core/PublicHeader/HashHelper.hpp 的公共 HashCombine，没有局部重复合并实现。保留必要的 std::hash 特化、哈希输入及合并顺序。

### 实施中遇到的问题

- 首次命名工具分析使用了错误的默认目标位数，并受现有 MSVC 扩展语法影响；不完整语义树遗漏了一些引用。该轮命名结果已撤回到仅完成编码修复的检查点，重新使用 x64 目标和完整分析后再改名。
- 分析时使用临时 VFS 覆盖，适配已有的冗余跨命名空间前置声明、未实例化模板中的旧调用和字符串宏拼接。覆盖文件仅位于 out/diagnostics/engine-style，不修改这些实际实现，也不参与 MSVC 构建。
- isLoaded 直接变为 IsLoaded 会与成员函数重名，最终按私有布尔成员规则统一为 m_bLoaded，并更新所有成员引用。
- 按访问权限改名时，工具遗漏了 InstanceDataMgr.inl 中 5 处依赖类型的友元成员引用；MSVC 实例化模板时报 C2039。已将管理器锁和实例 ID 数据的访问同步为 m_Mutex、m_InstanceIds、m_bInstanceIdsDirty，保持原有锁和更新流程。
- 编码修复与命名修改保留独立检查点及补丁，便于用户确认后分别审查、提交；当前没有执行 Git 提交或推送。

## Core 模块命名与注释编码统一

- 23 个源码/头文件中有 7 个旧编码文件，已正确转换为 UTF-8；按访问权限整理成员，统一参数和局部变量命名。公有向量分量统一为 X/Y/Z/W，并同步调用方的实际引用，保留第三方和原生 API 字段原名。
- Matrix 原有 Data() 访问器与拟采用的 Data 字段名冲突，因此公开存储字段使用 Elements；补齐未实例化的 Vec2、矩阵和 Octree 模板中的依赖引用，OctreeNode 的布尔字段使用 bLeaf。未改变布局、数学公式、锁或执行顺序。
- 本模块没有重复的 HashCombine 实现；保留公共 HashHelper.hpp 以及类型 ID 使用的独立 FNV-1a 算法，避免改变类型标识。
- 全项目 148 个翻译单元命名分析通过，Core 无剩余命名诊断；词法审计确认本批 1827 处标识符变化之外，只有注释编码变化，未改变其他 C++ token。MSVC Debug 的 Langcher、Tests 全量构建通过，MathTest、AssetOwnershipTest 返回 0，stderr 为空。

- 证据：`out/diagnostics/module-style/Core/` 下的 encoding.json、renames.json、audit.json、build.log、tests.json、runtime.json；窗口与运行日志为 `out/diagnostics/module-Core-after/`。本提交只包括 Core 调整及对应调用引用。
