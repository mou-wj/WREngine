# 故障与修复记录：光源节点、范围提示和地面网格

## 实现范围

基线为 `db2ed20`。EditorScene 将原先单独持有的四类预览光源并入 SceneComponent 节点列表；NodeEditor 按实际类型编辑属性。Renderer 新增 [HintRender.h](../../../src/Framework/Renderer/PublicHeader/HintRender.h)、[HintRender.cpp](../../../src/Framework/Renderer/Private/HintRender.cpp) 和 [HintRender.sf](../../../shaders/HintRender.sf)，通过既有 SceneViewDrawExtension 绘制地面网格及选中光源的范围，不修改 RHI 后端或 RenderGraphBuilder。

点光使用蓝色的三个正交大圆表示衰减球；聚光使用外锥底圆、16 条母线和轴向距离射线；平行光为箭头。XZ 网格位于 Y=0，以一世界单位为一米，根据相机到平面的垂直距离分为 0.1、0.2、0.5、1、2、5、10 米。初版采用 80×80 单元及边缘淡出，后续反馈后已替换为下文的全屏求交无限网格，平行光箭头也由两条头部线增加至八条。几何推导见 [提示算法](../../key_implemetion/algorithm/03-transforms-frustum-and-depth.md)，调用与所有权见 [Editor 架构](../../architecture/app/editor.md) 和 [生命周期](../../key_implemetion/performance/08-ui-rendering-and-window-lifetime.md)。

未打开工程时无场景节点，右侧属性栏折叠，视口只显示清空背景、网格与方向轴。打开工程创建四个默认光源节点；场景序列化尚未实现，重新打开不会恢复编辑过的节点参数。当前只显示选中光源的范围，天空光没有有限范围或变换编辑，平行光没有位移编辑。非天空光可编辑颜色、强度、投影，局部光可编辑范围，方向/聚光可编辑方向及旋转，聚光可编辑内外角；天空光颜色/强度未被现有 IBL 消费，因此控件明确禁用。

## 模型不可见：深度状态缓存发生确定性碰撞

### 现象与定位证据

完整 Editor 中创建工程、导入并投放 sphere.glb 后，节点存在，PrimitiveCount=1、可见网格和绘制 batch 都是 1，相机为 (2,2,2)，网格位置为原点，但画面只有天空与提示线。点光强度由 0 改为 50 后，场景纹理读回的明显变化像素为 0。直接场景入口在先创建光源时却能绘制模型，说明不能仅凭独立入口正常就判定 UI 流程正确。

对照实验把差异缩小为“是否先绘制过无光源空场景”：只改变视口宽高或先编辑灯光不复现；增加空场景首帧则复现。随后直接查询 RHI 缓存返回的描述符，记录为 `requested_write=1 requested_compare=1 returned_write=0 returned_compare=1`。

### 旧代码为什么返回错误对象

[RHIPipelineStateCache::HashDepthStencilState](../../../src/Framework/RHI/Private/RHIPipelineStateCache.cpp) 原先逐字段使用 XOR，且 GetOrCreateDepthStencilState 仅按 hash 命中，没有描述符比较。默认 Less 枚举值为 1，其他开关和两个 mask 默认都为 0：

| 调用方 | DepthTest | DepthWrite | Compare | 旧 hash |
| --- | --- | --- | --- | --- |
| 右上方向轴 | false | false | Less=1 | 0 XOR 0 XOR 1 = 1 |
| 模型/阴影 | true | true | Less=1 | 1 XOR 1 XOR 1 = 1 |

两个 true 相互抵消。空场景没有模型/阴影先创建深度状态，方向轴首先把关闭深度的对象存到键 1；之后模型命中同一对象，未写入场景深度。后面的天空绘制因没有模型深度而覆盖模型。先创建阴影状态只是改变哪个错误对象先进入缓存，不能消除缺陷。

### 修复与结果

只将该函数七个现有字段按声明顺序交给 Core::HashCombine。没有修改调用方正确的深度要求，没有新增缓存、等待或资源保活机制。修复后完整 UI 中模型恢复可见，点光 0→50 的场景读回有 **51,861 个像素**发生明显变化。Vulkan、D3D12 和 OpenGL 分别核查 32 组 depth-test/write/compare 配置，返回描述符均与请求一致。

这是已复现的字段抵消修复；缓存仍只用 hash 判等，其他缓存的遗漏字段/通用碰撞防护没有在本次一并重构。详细边界见 [状态缓存专题](../../key_implemetion/performance/06-shader-compilation-and-binding.md)。

## 光源属性更新、删除与空场景

- 原 NotifyComponentChanged 只标记 GPU dirty，上传仍从旧 LightSceneProxy 读取参数。现在先 UpdateFromComponent，再标记对应数据及阴影更新。LightComponent/PrimitiveComponent 没有独立类型 ID，原 IsA 会沿继承的 StaticTypeID 错误匹配；此入口改为检查 C++ 实际类型，没有扩大到类型系统重构。
- 原 RemoveLight 从移除命令中的空 LightProxy 标记脏数据，没有使用将被删除的实际代理。现在先取得已注册代理，更新脏标志、释放它已有的阴影分配并移除代理索引，然后删除代理。Sky dirty 时分别清除 diffuse/specular 引用，修复原来重复清 specular、遗漏 diffuse 的情况。
- 节点移除先等待既有视口访问完成值，若仍有未消费的 Add 则先 Flush，再 Remove/Flush 后销毁组件，避免 Add 后立即清理时 Remove 找不到尚未注册对象。没有新增 WaitIdle。
- 无方向光时，UpdateCascadeShadowInfo 曾无条件读取 `directionalLightShadowViewInfos[0]`，实际 UI 首帧触发 vector 越界断言并停在 CRT 对话框。该语句是未使用的调试结果，已移除；空矩阵数组也不再提交对应零字节上传。
- 三类光源空数组不再用空 data 上传一个兜底元素的大小。没有 Primitive 的帧只初始化背景、按需绘制天空并执行原视图扩展，不录制没有表面参与的材质光照计算。
- 网格/光源提示使用现有颜色和深度附件 Load_Store，测试深度但不写入。天空 Pass 的管线描述和实际附件都改为 Store 深度，供后续扩展使用；未引入自动 image-layout 管理。

## HintRender 实现中发现的问题

初版 Shader 把变量命名为 HLSL 保留字 `point`，造成 HintLineVS 编译失败，第一次 Launcher 验证未到首帧并超时结束。变量改为 worldPoint 后，两个阶段在三个后端均编译成功。C++ 所需 ShaderCompiler 头已显式包含，未靠传递包含维持编译。

最初网格片区以相机脚下为中心，远距离环绕看原点时，网格偏到画面下方。最终中心使用视线与 Y=0 的正向有限交点，并 floor 到当前间距；近平行或背向地面时回退到相机脚下。相机高度仍独立决定间距，没有把视线距离替代为垂直距离。近/远两端实际 GPU 读回已检查；有限片区仍会被视锥及远裁剪面裁掉，不宣称是无限地面。

## 后续修正：天空光唯一性及光源变换

天空光对环境整体生效，面板移除 Local transform、Position、Rotation、Scale 及所有变换工具按钮。当前没有独立启用开关，注册就是启用：Renderer::Scene::AddLight 检查已注册天空光和 pending Add/Remove 后的有效状态，同一对象重复注册幂等，第二个对象在 owner 和命令队列改变前明确报错。先 Remove 再 Add 可在同一 Flush 中替换，移除后允许重新注册；不同场景互不影响。没有增加通用光源启用系统或额外活动对象缓存。

平行光面板只保留 Rotation/Rotate，默认提示和旋转工具位置为原点；聚光保留 Position/Move 并增加 Rotation/Rotate；点光仍只有位移。Engine 的 DirectionalLightComponent 和 SpotLightComponent 在 OnTransformChanged 刷新 +X 前向，复用原 dirty/代理通知链。SetDirection 反解局部 Euler，因此保留直接方向输入，同时保证旋转工具改变的是实际照射方向。单方向不能决定滚转，直接改 Direction 按固定滚转约定处理；公式、父变换和单位见算法专题。

平行光箭头使用一根箭杆和沿垂直方向基底均匀展开的八条头部线，改善侧面辨识度。范围图形和实际光照仍从同一 GetDirection 读取，未增加编辑器私有朝向副本。

## 后续修正：全屏求交网格（历史方案）

有限 80×80 片区无法在宽投影和大幅平移时保证地面覆盖，单纯把它再放大仍存在边界。最终使用固定全屏三角形，像素通过逆 VP 与 Y=0 求交，以 frac 的周期函数生成网格线，fwidth 把线宽及网格密度转换为屏幕像素尺度。高度给出基础档，投影密度参与相邻档混合，实际档位限制在 0.1～10 米；不使用细分阶段，也不再生成 162 条世界空间线段。网格仅一次 Draw，但像素工作量增加，不能仅凭 Draw 减少声称性能全面提高。

首次实现包含 discard 和导数，DXC 产生 demote-to-helper SPIR-V 指令，桌面 OpenGL 的 SPIRV-Cross 报 `GL_EXT_demote_to_helper_invocation is only supported in Vulkan GLSL`。改为稳定分母和透明有效性掩码，保留 helper invocation，不修改公共编译器或后端；四个 Hint Shader 随后均通过三后端编译。

首次大幅平移测试虽仍覆盖画面，人工检查图片发现细线出现断点；绝对大坐标的逆投影和 frac 引入精度损失。最终在 CPU 移除相机 X/Z 的完整 10 米周期，重建网格专用相对 VP 和逆矩阵。所有显示档位都整除这个周期，图案仍锚定世界。相机整体平移 (10000,0,-30000) 后，GPU 读回与原图逐字节一致；未更改相机、场景矩阵或引擎坐标系统。

网格深度从交点投影重建，超过场景 far clip 的示意钳制到背景深度 1，以延续地面；已有模型仍遮挡线条，深度写入始终关闭。近平行、背向或无效交点输出透明。网格在地平线过密时自然淡出，不能在有限像素中保留无限多条线。

## 当前修正：可见地面 AABB 与单位网格细分

再次反馈网格效果时，先核对实际运行目录：常用 `out/build/vscode-x64-Debug/Renderer.dll` 仍为当日 02:00 的有限网格版本，上轮全屏求交验证使用的独立目录 DLL 则为 11:00。时间和构建路径证明两者版本不同，但不能据此认定用户的具体观察一定来自哪个实例。确认常用目录已无 Langcher 占用后，先将其更新，再在这个目录编译、运行当前方案；没有终止用户进程。

当前实现替换了上节的全屏求交：按视锥实际可见的地面范围绘制真实线段。只修改已有 HintRender 头/实现和 Shader，以及对应文档；不改 RenderCore/RDG、RHI 或后端。步骤如下：

1. 用网格专用相对 VP 的逆反投影视锥八角，根据 NO/ZO 选择近面深度。检查十二条边与 Y=0 的交点，求 XZ AABB；相机滚转或跨地平线时交面并非总是四边形，因此没有只检查四条角点射线。
2. 以相机距地高度选择 0.1～10 米间距，将 AABB 向外对齐整格、两侧各多留一格。不是固定范围再乘经验倍率，避免网格片区边缘落在可见地面内。
3. 固定 1×1 单位四角在 VS 中按 vertexId 展开两组平行线，映射到 AABB。CPU 提供区域、间距和细分数量，一个 Draw 提交 2(nx+nz) 个顶点，不重复每个小单元的共享边，也不分配逐帧 VBO/IB。
4. PS 根据相邻平行线在屏幕上的垂直间隔淡出过密线；10 米主线保留较亮颜色。由硬件裁剪、深度插值及已有深度测试处理遮挡，不再逐像素求交、不写 SV_Depth，也不把 far 之外的地面钳成背景深度。

当前 RHI 的图形阶段描述仅接入 VS/PS；Vulkan 管线没有配置 tessellation state，D3D12/OpenGL 对应管线也未接入 HS/DS。完整硬件细分需要更改公共描述、缓存与三个后端。本轮采用已说明的较小范围方案：CPU 按视图确定细分数量、VS 展开真实网格线；没有声称已实现 GPU 硬件细分，也没有新增通用渲染接口。当前整块 AABB 使用统一高度档位，远处按投影密度淡出；不是沿视线逐区间调整几何 LOD，档位切换仍离散。详细公式、复杂度和退化情况见 [算法专题](../../key_implemetion/algorithm/03-transforms-frustum-and-depth.md)，快照及提交见 [工程专题](../../key_implemetion/performance/08-ui-rendering-and-window-lifetime.md)。

实现中的兼容问题：Core::Float2 构造函数不是 constexpr，矩阵乘法接收 std::array 而非 Float4，局部代码分别使用 const 四角和 std::array 齐次向量，未修改公共数学库。首次 Shader 将线编号命名为 HLSL 的 line 修饰关键字，导致 HintGridVS 编译失败；改为 lineIndex 后四个阶段均通过三后端编译。复核时修正细分数量的端点计数，确保 AABB 两侧确实各有一个整格余量。

## SceneSetting 控制 Hint，移除编辑器直接依赖

原先 SceneEditor 在 DrawExtension 中直接调用 Renderer::HintRender::AddGridPass/AddLightPass，因此 CMake 链接 Renderer，apps.json 也声明 SceneEditor→Renderer。将绘制入口放在扩展中本身并不要求这个依赖，直接依赖来自调用具体模块的导出函数。

按场景设置控制绘制后，现行调用链为：

```text
EditorScene::Initialize / Select
    → SceneInterface::GetSceneSetting()
    → RenderModule::BeginRender 复制设置
    → 场景主体 → 按开关添加 Hint → 上层 DrawExtensions → 原 builder.Execute
```

SceneSetting 定义和存储均在现有 SceneInterface.h，没有新建文件或管理器。bDrawGrid/bDrawLightHints 默认 false，LightHintTarget 默认 nullptr；目标非空且光源开关开启才绘制该对象。Editor 开启两类提示，选择光源时填写目标，选择网格/清空选择时置空。Renderer::Scene::RemoveLight 清空匹配引用；仍要求调用方按原 Remove/Flush 顺序销毁组件。设置在控制线程上、BeginRender 之前修改，构图时复制参数到 arena，不增加异步共享状态、保活容器或等待。

SceneEditor 移除 HintRender 包含/调用及 PRIVATE Renderer 链接；apps.json 中 SceneEditor 只显式依赖 Engine。应用模块列表仍保留 Renderer 作为 RenderInterface 的实际实现，Editor 经 SlateRHIRenderer 原有依赖保证启动/关闭顺序，不能把“无直接代码依赖”理解为运行时无需 Renderer。具体职责及借用边界见 [Engine](../../architecture/engine.md)、[Renderer](../../architecture/render/renderer.md) 和 [UI 生命周期](../../key_implemetion/performance/08-ui-rendering-and-window-lifetime.md)。
