## 工程基础层快照的 IBL 初始化完成点

前置实现见 [11 月 3 日工程快照记录](故障与修复记录-2026-11-03.md#改为只保存纹理基础层)。普通纹理只保存基础层并重建 Mip，天空光只保存环境输入并重新预计算 IBL；文件格式、所有权和调用链见 [工程快照实现](../../key_implemetion/performance/10-project-snapshots.md)。

### 现象与根因

工程用例已退出 0，场景和天空光保存重开像素也一致，但 project-base-mips-ui.stderr.log 仍有 7 条 VUID-vkDestroyImageView-imageView-01026：VkImageView 在对应 VkDescriptorSet 的提交尚未完成时销毁。因此不能把进程退出和像素通过说成资源生命周期验证通过。

[当时的 SkyLightAsset::Create（现已迁入环境光管理器 Build）](../../../src/Framework/Engine/Private/EnvironmentLightResourceManager.cpp) 复用 PreComputeIBL 后立即返回。PreComputeIBL 已提交 Compute，并在输入及两张输出记录同一个实际 Fence；返回并不代表 GPU 完成。ProjectArchive 加载随后还会校验父关系、数值等数据，拒绝恢复时会释放已创建但未注册的资产，独立加载对象也可以很快释放。新恢复路径没有等待初始化完成，六个 specular 视图和一个 diffuse 视图可能仍被计算使用。

### 修复

在 SkyLightAsset::Create 完成预计算提交后、返回资产前，读取 specular 输出 Tracker 的实际 Fence 并 WaitValue。它与 diffuse 属于同一提交，因此只需等待一次。等待属于同步恢复资产的初始化阶段，不移入通用析构，不增加 WaitIdle、延迟回收容器或后端特例；后续渲染使用仍遵循已有显式完成点。普通纹理重建和只保存基础层的逻辑保持不变。

## 环境光计算产物改由 Engine 管理

### 职责和交互调整

环境输入可作为 TextureAsset，但 diffuse/specular IBL 是计算产物，定义为 SkyLightAsset 会混淆文件资产和运行时生成结果。按新的职责划分，删除 SkyLightAsset.h/.cpp，在 Engine 增加 EnvironmentLightResourceManager.h/.cpp，管理构建、按输入对象身份复用、应用及显式释放。EnvironmentLightResource 是同一头中的非资产结果对象，只有输入及两张生成纹理。SkyLightComponent 持有使用引用，贴图 Getter 读取该结果，不再暴露裸 IBL Setter；AssetManager 不再包含或创建天空光资产。

新建天空光使用管理器创建的中性灰默认环境，原 Application 同步改为这一行为，不自动加载示例 HDR 图片。默认输入为管理器自己的 1×1 UNorm 像素，无 TextureAsset 或文件依赖；工程 environment=0 表示默认，默认输入及生成输出均不写盘。用户输入仍只保存基础层，加载由管理器重新预计算；已有基础层快照格式保持兼容。

天空光 EnvironmentTexture 通过通用 ComponentProperty 追加 TextureAsset 引用类型。资源面板单击图片即可加载并选中；NodeEditor 用宿主回调获取该选择，Use selected texture 调用管理器构建、应用，Reset 恢复默认。没有单独的天空光属性面板或功能模块相互依赖。输入会被显式纳入工程内容，因此应用后及源文件不再存在的重开场景中，Project data 都显示输入 TextureAsset。属性赋值失败显示错误并保留旧绑定。

构建继续等待实际 IBL 初始化 Fence，再发布结果，不增加 WaitIdle。普通场景删除、清空及关闭在原完成点之后 ReleaseUnused；加载失败在局部恢复节点销毁后清理未引用结果；Engine 关闭时清管理器拥有引用。原 Application 还补齐遗漏的 SkyLightComponent 删除，避免使用引用泄漏。实际调用链、线程边界、缓存和 GPU 生命周期见 [环境光工程实现](../../key_implemetion/performance/05-assets-materials-and-instance-data.md#环境光计算产物管理)，总体边界见 [Engine 架构](../../architecture/engine.md)。

## 资源目录操作与单文件导入

### 问题与调整

原资源浏览器没有文件/目录层级编辑入口，ImportFile 对所有输入都创建包目录，所以单张图片也产生一层无意义目录。现在目录树与卡片共用条目动作，支持拖放文件或目录到文件夹、重命名、右键创建目录和确认删除。图片直接复制到当前目录；自包含 GLB/JSON 在校验后发布为独立文件，只有外部依赖确实被复制时才保留包目录。文件/目录重名避让或拒绝，不覆盖既有内容。

移动不能只 rename 磁盘文件：材质的 textureParameters、glTF buffer/image URI 仍以旧文档目录解析，已加载资产也仍以旧规范化路径缓存。为此在 AssetEditor 的独立成员实现文件 EditorAssetFileOperations.cpp 中准备本地引用改写，处理引用目标和引用者同时移动、空格 URI 编码及整包移动；其他文档仍引用目标时拒绝删除。根、目录自嵌套、符号链接和越出 Content 的路径受检查。

Engine 只补充源路径协调：IAsset 的受保护 SetSourcePath、三个文件资产的覆写、AssetManager::UpdateSourcePaths 和 AssetRegistry::Unregister。移动不替换资源对象/名称，只迁移源路径、强弱缓存键和 Registry；删除解除文件关联，已有所有者继续持有实际资源。这样移动后再次加载不会重复创建同一资产，删除后同名重新导入也不会命中旧对象。没有修改 RHI、RenderCore、Renderer 或 src/Tests 流程，没有新增资源管理器、全局保活列表或 GPU WaitIdle。

### 执行顺序与开发中处理的问题

- 菜单和拖放先复制操作参数，下一次 DrawContent 在遍历目录及卡片之前处理，避免修改遍历中的缓存。重命名、删除源目录后修正选择、当前目录、历史及待导入路径。目录树的材质点击延迟到松开且未拖动，保留场景网格/材质的原载荷类型。
- 文件读取可能来自 AssetManager 的 async loader，因此 WaitForLoads 放在改磁盘前。路径表更新只接受已完成加载的控制线程调用，不把等待放在 Manager 锁内；被移除驻留引用在锁外析构。该接口不支持任意线程并发改文件或从加载回调重入。
- 路径映射对源本身直接返回目的路径，不能把相对结果 `.` 拼成文件名后的 `/.`；后代才拼接相对路径。UI 载荷/JSON 使用 UTF-8，调用 Engine 路径 API 继续使用既有 filesystem::generic_string 约定，不宣称本次修复了所有底层 Unicode 路径限制。
- 普通 JSON 写入失败会尝试恢复原文和移动，恢复失败也明确报告；没有断电事务或回收站。未知/损坏 JSON 不猜测依赖，手动放入的外部引用 GLB 不在改写范围。删除发生 IO 错误时可能已删除部分目录项，不能承诺回滚。
- 临时 UI 驱动最初把删除标题里的 Delete files 当成按钮，以及在移动选择跟随到目标目录后仍从旧目录找卡片，导致断言失败。修正驱动按实际按钮行定位并显式导航；没有为配合测试改变界面行为或降低断言。所有实际文件操作均在独立诊断工程中执行。

## 纹理画布主轴、中键平移与场景坐标主轴

### 调整及原理

TextureViewer 原来只接受左右键，背景网格没有独立原点标识。EditorTextureViewer::DrawCanvas 现在由同一个 InvisibleButton 接受 Middle：在空白和图片上都只改画布 Pan，不改选中项和图片逻辑中心。原空白左键平移、图片左键移动、滚轮锚点缩放继续保留。背景零线不再按普通灰网格重复绘制，改为固定 2 个界面单位宽的红 X/蓝 Y，并标注 +X/+Y 和 0；主轴随画布变换，图片仍覆盖其背后的网格。坐标和公式见 [画布算法](../../key_implemetion/algorithm/09-texture-viewer-canvas.md)。

HintRender 原网格按相机的 10 米周期重定位，局部零点不是世界零点。因此增加 HintGridParameters::GridAxes，保存 CameraRelative-CameraWorld 的 XZ 分量；VS 将沿 X/Z 的线分别与正确的全局零线比较，使用红 X/绿 Z、高于普通网格的 Alpha。轴标记经 LineData.w 进入 PS，仅跳过重复平行线的投影密度淡出，保留原深度、距离淡出和裁剪，不增加绘制 Pass、原生宽线依赖、等待或资源管理逻辑。原点补偿推导见 [场景网格算法](../../key_implemetion/algorithm/03-transforms-frustum-and-depth.md#xz-地面网格与光源提示几何)。
