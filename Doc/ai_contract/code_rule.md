# AI 代码修改契约

本契约适用于本仓库的代码修改，包括 C++、Shader、测试、构建脚本及影响程序行为的配置。目标是：先理解需求与现有架构，再以最小必要改动完成任务，并提供真实的验证结果。

## 1. 每次修改前必须重新读取

- 每次开始一项代码修改任务，以及同一任务中开始下一批独立修改或继续修正代码前，都必须从磁盘完整读取本文件，逐条确认适用要求。不能只依赖上一轮对话、记忆或摘要。
- 恢复中断任务、切换会话或上下文压缩后，修改前同样必须重新读取。
- 同时检查适用于目标目录的 `AGENTS.md`、相关模块开发约定及用户在当前任务中给出的限制。
- 用户对当前任务的明确要求优先于本契约的一般约定；仍须遵守运行环境的上级指令。遇到实际冲突时说明冲突，不能自行忽略。
- 本文件是约束，不是背景资料。修改前的分析、实施中的取舍和交付前的检查都必须遵循。

## 2. 先分析需求，再修改代码

- 明确用户要解决的现象、期望行为、允许修改的范围、禁止修改的内容和验收方式。
- 阅读相关架构文档、现有实现、调用方与同类实现，确认模块职责、数据流、资源生命周期和执行顺序。不能仅凭文件名、接口名或经验猜测实现。
- 修复问题时，先收集报错、日志或复现证据，沿调用链定位原因。区分已确认的根因与待验证的推测，不得把猜测当作结论。
- 动手前简要说明判断依据、拟修改位置和验证方式；常规且已获授权的工作直接推进，不要求用户反复确认。
- 信息不足时先完成不依赖缺失信息的检查。只有缺失信息会实质改变实现或无法满足明确限制时，才提出具体问题。

## 3. 实施最小必要改动

- 只修改实现当前需求或修复已确认问题所必需的代码，不顺带重构、整理命名、升级依赖、调整目录或增加未来功能。
- 优先复用并扩展现有类、函数和文件。新增文件、公共接口、抽象层或依赖前，先确认现有结构确实无法合理承载，并说明必要性。
- 最小改动以正确性和职责归属为前提，不能为了减少行数而绕过架构、复制逻辑、硬编码特殊值或隐藏错误。
- 保持现有接口与默认行为；需求明确要求改变的部分除外。接口变更须核对所有调用方及后端实现。
- 若用户限定文件、模块或可修改内容，严格遵守。发现必须超出限制时，先说明证据与最小扩展范围，取得明确同意后再修改超出部分。
- 新发现的无关问题记录为后续事项，不擅自扩大本次任务。

## 4. 尊重现有架构与抽象边界

- 按照 `Doc/architecture` 的相关说明理解设计，并对照源码确认实际行为。文档与源码不一致时明确指出，不能假定任一方必然正确。
- 共性逻辑归属公共抽象层，平台或图形 API 差异归属对应后端；不能把后端缺陷转嫁给上层调用方。
- RHI 的接口、枚举和资源语义应在各后端保持一致。RHI 枚举到原生图形 API 枚举的转换放入对应的 `xxxUtils`，遵循现有模块组织。
- RenderCore、Renderer、RHI 和窗口/UI 层保持既有职责，不引入不必要的反向依赖或跨层访问。
- 不支持的能力应提供准确的能力检测和明确错误；不能返回伪成功、静默忽略命令或擅自增加回退实现。
- 涉及资源、异步任务和图形命令时，核对所有权、释放时机、线程/上下文要求、CPU/GPU 同步、状态转换与对齐约束。

### 4.1 命名、编码与公共工具

- 项目自有类、结构体、函数和成员函数使用 `PascalCase`。数据成员按声明的访问权限命名：私有成员使用 `m_` 加 `PascalCase`（如 `m_Mutex`），保护成员使用 `_` 加 `camelCase`（如 `_localLocation`），公有成员使用 `PascalCase`（如 `Width`）；类和结构体遵循同一规则，不为改名改变访问权限。
- 布尔成员在访问权限前缀后使用 `b` 加 `PascalCase`，例如私有 `m_bLoaded`、保护 `_bVisible`、公有 `bDepthTestEnabled`；函数参数和局部变量使用 `camelCase`，例如 `materialIndex`、`textureDesc`。
- 标准库、第三方和原生图形 API 的字段、回调及必须匹配的重写接口保留原名。模板参数、宏和具有绑定意义的标识符需按其实际用途处理，不能机械改写。
- 命名迁移逐模块实施，同步更新其他模块中的实际引用；检查模板、哈希特化、Shader 反射与序列化约定，保证行为不因改名变化，不顺带整理调用方的无关代码。
- 项目自有源码统一使用 UTF-8。迁移旧文件时先确认原编码，再转换并保留换行；已损坏的注释从历史恢复或依据实现准确重写，不能将乱码原样另存为 UTF-8。编码修复与命名迁移保留可分开审查的差异。
- 优先复用 `Core/PublicHeader/HashHelper.hpp` 中的公共 `HashCombine`，不新增局部重复实现；保留各类型必要的 `std::hash` 特化和等价比较，统一工具时不得无意改变哈希输入、合并顺序或持久化数据语义。

### 4.2 严格遵守设计，不为跑通流程引入临时概念

- 实现必须服从用户已确认的设计思路、模块职责和资源管理约定。编译通过、测试通过或演示能够运行，都不能作为偏离设计、扩大修改范围或引入额外概念的理由。
- 不得为了绕过局部问题，临时创造 Frame、Manager、全局保活列表、重复缓存或其他管理机制，再让现有框架配合这些机制修改。不能把实现过程中自行引入的依赖，当作原设计必须改造的证据。例如，材质职责调整不应自行扩展为 MaterialFrame、retained 容器及 RenderGraphBuilder 生命周期改造。
- 新增概念或机制前，必须说明已确认的具体问题、现有机制为何无法承担、实际调用方、职责归属，以及所有权和执行时序；同时比较直接修正现有实现的方案。没有当前需求和代码证据支持的必要性，就不增加，不能仅以“更通用”“以后可能用到”或假设风险为依据。
- 项目采用显式资源状态、访问 Fence 或生命周期控制时，必须沿用其设计，不得擅自用全局持有、自动回收、额外等待或其他隐式机制改变控制方式。状态与访问记录应在实际操作和提交的位置维护，不能为适配新增机制而迁移到无关层级。
- 如果已确认的问题确实需要改变既定设计，先说明证据、冲突、影响和最小调整方案；超出用户已授权设计或范围的部分，须先对齐后实施。不能先做临时方案跑通，再将其作为最终设计交付。
- 验收必须同时检查功能正确和设计一致。交付前逐项核对新增概念、容器、接口、缓存和同步操作的必要性；撤销不必要机制时，一并清理仅为它增加的调用、依赖、专用测试和现行文档描述，不保留无实际用途的框架。

## 5. 保护工作区和现有代码

- 修改前检查工作区差异，区分已有修改与本次修改。不能覆盖、回退或清理用户及其他任务的工作。
- 保留文件原有编码、换行和局部代码风格，避免整文件格式化、无关空白变动和批量替换造成的差异。
- 不擅自执行提交、推送、强制重置、清理工作区、删除构建目录等操作。用户已明确授权的操作按授权范围执行。
- 完成修改与验证后，由用户认可并明确通知执行 Git 提交和推送；仅完成任务或收到一般认可，不代表已获得提交、推送授权。收到明确通知后按授权范围执行，无需重复确认。
- Git 提交信息统一使用 `ai_code: 本次提交的修改内容描述` 格式；保留 `ai_code: ` 前缀，后面填写本次实际修改的具体描述。
- 提交前核对差异和暂存内容，只包含用户本次授权提交的修改，避免混入其他工作。
- 不通过删除功能、吞掉异常、关闭校验或降低错误级别来掩盖故障。
- 临时诊断日志、截图和脚本放在合适的临时或忽略目录；最终差异只保留必要内容，不引入机器专属路径或敏感信息。

## 6. 测试不能迁就错误实现

- 修复实现时，优先保持现有测试输入、Shader、资源访问声明、执行流程及验收标准，确保测试仍能暴露原问题。
- 用户限定测试只能切换测试项、RHI 或添加日志时，不得改动测试主流程、期望结果、渲染参数或资源语义。
- 不允许修改上层正确的调用方式来适配某个后端的错误转换或实现。
- 确需修正测试自身的问题时，先给出独立证据；若超出已授权范围，先取得同意。
- 新增或调整测试应验证实际行为与回归风险，避免仅重复实现细节。简单、可逆的改动不为凑数量新增测试。

## 7. 验证必须对应需求

- 先完成与修改相关的编译和必要检查，再运行能够覆盖问题的测试；多后端共用逻辑变更应检查受影响后端。
- 配置成功、编译成功、程序启动、功能正确和正常退出是不同的验证结果，必须分别说明，不能互相替代。
- 涉及渲染结果时，结合运行日志和实际画面或读回结果判断；不能仅凭窗口出现或没有异常断言功能正常。
- 修改影响启动、渲染主链路，或用户明确要求时，需要运行 `Launcher`（项目中实际命名可能为 `lancher`）验证，不能只编译测试程序。
- 因长循环而主动停止、因环境限制无法运行、只验证部分帧或存在校验错误时，明确记录实际范围与限制，不能宣称完整通过。
- 使用针对性的验证。检查通过后，只有新改动、新失败或未解决的风险才需要重复或扩大检查。

## 8. 文档与交付要求

- 文档描述必须对应真实源码和已执行的验证，区分已实现、已验证、已知限制和待办项。
- 正式文档必须独立可理解，以已入库的源码和稳定文档说明设计与依据；不得把未入库的临时需求清单作为来源、链接或理解前提。临时验证产物可以记录位置，但必须同时写明可核查的操作、范围和结果。
- 涉及架构或公共接口变化时，按必要范围更新 `Doc/architecture` 中的相关说明，避免文档与实现脱节。
- 需要记录故障或开发中遇到的问题时，使用 `Doc/dev/bugfix/故障与修复记录-YYYY-MM-DD.md`，写明现象、根因、修复方式、验证结果和未解决事项。
- 与本次修复无关的改进建议、接口限制和后续优化，按需记录到 `Doc/dev/optimize/优化点-YYYY-MM-DD.md`，说明问题、影响及建议，不将建议写成已完成实现。
- 使用实际工作日期；同日已有对应文档时优先补充，不重复创建同类报告。简单修改无须额外生成报告。
- 交付时简要说明改了什么、为什么这样改、执行了哪些验证，以及仍存在的限制。没有执行的检查必须明确说明，不能编造测试、日志或画面结果。

### 8.1 核心实现必须形成可核查的开发文档

- 所有涉及核心框架、并发、内存管理、关键算法及其原理的开发，都必须同步整理文档，不能只交付由 AI 生成的实现，让开发者无法掌握细节。
- 核心框架的模块职责、依赖、接口和总体数据流继续按 `Doc/architecture` 现有目录组织；工程实现细节（线程、队列、同步、所有权、内存分配与回收、缓存等）整理到 `Doc/key_implemetion/performance`；数学、几何、图形算法及推导（例如射线与三角形求交）整理到 `Doc/key_implemetion/algorithm`。目录统一使用这里的实际拼写，不另建近似拼写的平行目录。
- architecture 已提及但不够详细的内容，应在核心实现目录补充并双向关联；尚未提及但属于核心细节的实现，同样必须纳入。避免复制多份互相冲突的现行说明。
- 工程文档必须说明实际调用链、关键数据结构、线程或上下文归属、锁与等待关系、CPU/GPU 完成点、资源所有者、分配/复用/释放条件、异常和关闭路径，以及可能的性能代价。
- 算法文档必须说明输入输出、坐标与单位、数学原理或推导、公式与源码变量的对应、执行步骤、复杂度、精度和退化情况；必须区分标准原理与项目当前实现，不能把算法名或注释当作实现正确性的证明。
- 文档须链接真实源码、列出关键符号和可复查的验证入口，区分已接入、仅有实现、占位和已知限制。发现代码与设计/原理不一致时如实记录，不得编造保证，也不得借整理文档擅自修改实现。
- 修改相关实现时同步更新对应专题、索引及覆盖清单；交付前核查文档与本次源码一致。文档整理任务应记录检索范围和未覆盖内容，不能把关键词扫描说成逐行审计，或把源码分析说成运行验证。

## 9. 修改前后自查

修改前确认：已重新读取本契约；已理解需求和相关架构；已检查工作区；已确定最小修改范围与验证方式；拟新增概念和机制具有当前需求支持的必要性，且符合已确认设计。

提交结果前确认：差异均与需求相关；未越过用户限制；未破坏抽象或测试语义；没有为跑通流程遗留不必要的概念、机制或配套依赖；核心框架及核心实现文档已同步；临时内容已妥善处理；验证与文档表述真实一致。
