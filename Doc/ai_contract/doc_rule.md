# AI 文档修改契约

本契约适用于仓库文档的新增、修改、移动及删除，也适用于代码开发后同步整理架构、实现原理和开发记录。目的是让开发者能够根据文档理解真实实现、核查设计和验证结果，避免项目逐步依赖无法追溯的 AI 开发细节。

## 1. 修改前完整读取并确认范围

- 每项文档任务、同一任务中的后续独立修改，以及中断或上下文压缩后的继续修改，都必须从磁盘完整读取本文件，不得只凭记忆或摘要执行。
- 同时检查适用的 `AGENTS.md`、目标目录约定、相关文档及实际源码。涉及代码、Shader、测试、构建脚本或行为配置修改时，还必须完整读取并遵守 [AI 代码修改契约](code_rule.md)。
- 先确认本次需要补充的事实、所属目录和已有说明，只修改相关内容。优先补充现有专题，不顺带重排目录、整篇重写或新增重复报告。
- 保留用户已有修改。文档整理本身不授权修改代码、改变设计或执行 Git 提交和推送。

## 2. 按现有目录组织内容

- `Doc/architecture` 保存核心框架的模块职责、依赖、接口、总体数据流和扩展方式，沿用现有目录结构。
- 只有实际涉及架构职责、模块关系、公共接口或主流程变化时，才更新对应 architecture 文档。与架构关联不大的独立功能实现、局部算法、调试细节和阶段性回退记录，放入对应实现专题或开发记录，不因新增了功能或修改了某模块代码就向架构文档追加说明。
- `Doc/specification` 保存架构已提及、确有进一步说明必要，但不属于 `Doc/key_implemetion` 核心工程或算法细节的内容，例如模块功能约定、使用流程和接口使用限制。架构中保留必要概述，详细说明写入该目录下对应模块的文档，并在相关章节按需关联，避免将这些细节堆入架构文档。
- specification 文档按模块组织，文件名使用小写模块名加 `_spec.md` 后缀，例如 `renderer_spec.md`。同一模块优先补充已有文件的对应章节，不为每次功能调整新建一份文档。
- `Doc/key_implemetion/performance` 保存并发、线程、队列、同步、资源生命周期、内存分配与回收、缓存等工程实现细节。这里的 performance 是工程分类，不代表已完成性能优化。
- `Doc/key_implemetion/algorithm` 保存数学、几何、图形及其他关键算法的原理、推导和实际实现，例如射线与三角形求交、投影变换、QEM、光追 AS 与 SBT 中的相关算法。
- architecture 已提及但解释不充分的内容，按性质选择补充位置：核心工程和算法细节写入核心实现目录，其余确有记录必要的功能或使用说明写入 specification。确有架构关联时，在相应架构章节简要链接并由专题链接返回。未提及但影响理解核心实现的内容，也应纳入适当专题，不要求为此向架构文档新增独立功能介绍。
- 核心实现目录统一使用项目现有拼写 `key_implemetion`，不另建近似拼写的平行目录。已有专题包含跨类别内容时，优先保留组织方式并补充交叉链接，不为分类强行拆分。
- 故障、修复和实现中遇到的问题写入 `Doc/dev/bugfix/故障与修复记录-YYYY-MM-DD.md`；尚未实施的优化建议写入 `Doc/dev/optimize/优化点-YYYY-MM-DD.md`。
- 日期采用实际工作日期。同日已有记录时补充已有文件；简单文案修改不必另建过程报告。

## 3. 以真实源码和稳定资料为依据

- 正式文档必须独立可理解，以项目源码和稳定文档说明设计依据，准确使用真实的类型、函数、字段和路径，不能凭经验假设接口存在。
- 不得将 `task.md`、类似临时任务清单、未入库草稿或会话上下文作为正式文档的来源、链接或理解前提。开发记录应直接描述需求、设计和事实，不写“按临时任务文档要求”之类的引用。
- 遇到既有临时文件引用时，在本次相关范围内改为完整说明或稳定引用。用户明确要求全量清理时，检索相应文档范围并逐项处理，不能只删除链接却留下缺少解释的内容。
- 临时日志、截图和脚本放在合适的忽略目录。文档可以记录诊断产物位置，但必须同时写明可复查的操作、条件和结果，不能让未入库产物成为理解结论的唯一依据。
- 区分已实现、已接入、已验证、已知限制和待办项。占位接口、注释和 TODO 不能写成已完成能力。
- 发现源码与架构或标准原理不一致时，明确说明差异和影响；未定位的原因标为推测或待查，不把算法名称或注释当作正确性证明。

## 4. 核心实现应解释到可核查的程度

- 所有涉及核心框架、并发、内存管理、关键算法及其原理的开发，都必须同步整理相关文档，不能只留下实现代码或一句功能摘要。
- 架构说明应写清模块边界、依赖方向、公开入口、调用方、数据流及扩展位置，并链接详细实现专题。
- 工程实现说明应写清关键数据结构、调用链、线程或图形上下文归属、所有权、分配与复用条件、释放时机、锁与等待关系、CPU/GPU 完成点、失败及关闭路径，以及实际性能代价。
- 算法说明应写清输入输出、坐标系与单位、数学原理或推导、公式与源码变量的对应、执行步骤、复杂度、精度、边界和退化情况。
- 明确标准原理与项目当前实现的区别。采样估计不能写成严格误差上界，局部实现不能写成完整支持某个系统。
- 使用真实源码链接、关键符号和可复查的验证入口帮助开发者定位实现。伪代码和示意图用于解释时，应标明其用途，避免与实际执行代码混淆。

## 5. 故障与修复记录要说明因果关系

- 记录具体触发条件、现象、报错内容和报错位置，沿调用链说明上层传入了什么，以及与下层判断条件或资源状态在哪一点不匹配。
- 根因已确认时，说明数据为何会变成该状态、原实现怎样处理、错误机制如何产生，以及修复为何能够消除问题。必要时给出实际捕获的输入值、哈希或布局信息，不编造未记录的数值。
- 写清实际修改位置、修复策略、影响范围、验证结果及未解决事项，区分根因修复和仅缓解现象的措施。
- 同一问题后续取得新证据时补充时间和结论，说明先前推测是否被证实。历史阶段的记录保留时间语义，现行架构和实现专题应同步更新为当前事实。
- 优化建议需说明现状、影响和建议，不能与已完成修复混写，也不能将未经测量的性能判断写成基准结果。

### 5.1 发现的优化点必须同步归档

- 在需求分析、开发、代码审查、验证或交付说明中发现并明确提出的优化点、尚未补齐的能力、接口限制和性能改进建议，必须同步记录到 `Doc/dev/optimize/优化点-YYYY-MM-DD.md`，不能只留在会话回复、源码 TODO、故障记录或实现专题的“已知限制”中。仅分析而未修改代码的任务同样适用。
- 记录前检索该目录已有条目；同一问题优先补充原条目的状态、证据和关联链接，不在不同日期重复创建独立待办。同日的新问题补充到当日文档，没有当日文档时使用实际日期创建。已有实现专题保留事实说明，优化记录链接对应专题及源码，不重复复制完整实现原理。
- 每项至少写明当前状态、可核查的现状或依据、影响、建议方向和验收条件；按需要注明优先级及前置依赖。区分待实现、待测量、待验证与已完成，推测的收益不能写成已证实的性能瓶颈或基准结果。
- 后续实施某项优化时，必须同步更新原条目的进展；完成后关联实际实现说明和验证记录。故障仍按本章要求记录到 bugfix，优化记录不能代替故障根因与修复记录，也不构成擅自实施该优化的授权。
- 交付前逐项核对本次明确提出的优化建议是否已有对应记录，补齐遗漏并提供文档位置；不能仅因其他文档已经提过就省略 optimize 中的条目。

## 6. 验证记录必须与实际操作对应

- 分别说明配置、编译、启动、功能结果和正常退出的验证范围，不能相互替代。写明必要的测试入口、后端、配置、输入和结果，避免只写“测试通过”。
- 涉及渲染时，用画面检查或像素读回等证据说明结果；窗口出现、进程存活或首帧提交不代表完整画面正确。
- 主动终止、超时、异常退出、环境限制及已有校验错误必须如实记录。最终成功复测与此前失败分开描述，不能用后续成功覆盖尚未解释的问题。
- 没有运行的检查明确说明未执行。文档检索和源码分析不能写成运行验证，关键词扫描不能写成全量逐行审计。
- 记录全量整理的检索范围、排除项和未覆盖内容。修改相关实现时同步维护必要的专题、索引与覆盖清单；涉及行数或内容摘要的清单应与当前源码一致。

## 7. 保持内容、编码和引用可维护

- 使用清晰中文和准确技术术语，按逻辑分段，必要时使用列表、表格、公式或示意图。避免大段无结构堆叠，以及脱离当前实现的泛化介绍。
- 补充内容前先通读目标文档的章节结构，按主题、上下文和阅读顺序确定写入位置。优先修改或补充对应章节中的现有说明；确需新增章节时放在逻辑相关的位置，并保持标题层级、编号和目录一致。
- 不得习惯性地将新功能、开发日期、修复摘要或回退说明插到文档开头，也不得机械堆到末尾。开头保留文档定位和总体说明，开发过程与时间线写入开发记录；只有内容本身属于总述或文档结构明确要求时，才调整开头。
- 文档使用 UTF-8，保留原文件合理的换行和局部格式。乱码应依据历史或真实内容修复，不能将损坏文字原样另存。
- 仓库文档链接优先使用相对路径，核对目标文件和标题锚点。源码移动、接口改名或标题调整后，同步修正相关引用，避免机器专属绝对路径。
- 一个事实优先维护在对应主文档中，其他文档简述并链接，不复制多份逐渐分歧的现行说明。
- 删除已撤销机制时，同步清理仅为该机制增加的现行说明、示例和索引，历史记录应明确该方案已撤销，避免读者误认为仍在使用。

## 8. 交付前检查

- 核对文档与实际差异，确认未覆盖用户已有内容、未引入无关改动，目录、命名、日期和来源符合约定。
- 核对链接、代码片段、公式与变量、术语、索引及必要的覆盖清单，检查 UTF-8 编码和 Markdown 结构。
- 核对本次明确提出的优化点是否已归档到 `Doc/dev/optimize`，以及本次已实施的优化是否同步更新了原条目状态和验证依据。
- 纯文档修改执行针对性的内容、链接和差异检查；只有代码、构建或行为受影响时，再按代码契约执行相关编译和运行验证，不为文档修改虚构测试结果。
- 最终简要说明修改了哪些文档、整理了什么、执行了哪些检查及尚存限制。提交和推送仍遵循代码契约中的授权要求与 `ai_code: 本次提交的修改内容描述` 格式。
